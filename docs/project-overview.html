Compliance Copilot

A .NET 10 AI agent for a fictional company-compliance SaaS platform: RAG over public regulator guidance for general knowledge, MCP tool calls over mocked user data for account-specific facts, and two deterministic verification mechanisms that catch the model when it gets things wrong.

1. Overview

The scenario: a SaaS platform for accounting/bookkeeping firms needs an AI assistant that can answer two genuinely different kinds of question, and must always know which one it's answering. A general-knowledge question ("what happens if I miss my annual review?") is answered from a small RAG corpus of real public regulator guidance. An account-specific question ("when is my next review due?") is answered by calling tools over a genuinely separate MCP server, backed by mocked user data. A realistic query needs both at once.

The brief weights judgement — not features — as the dominant scoring criterion: knowing where to let the model reason freely and where to constrain it with code, and having a real, demonstrated way of catching the model when it's wrong. Every design decision below is made with that in mind first, UI polish a distant last (the brief explicitly puts it out of scope).

4. Agentic vs. deterministic

The single sentence this build is organised around: the LLM proposes, deterministic code disposes — it never gets the last word on whether something is true.

StepWhoWhy
Extracting intent/entities from free textAgenticGenuinely needs language understanding.
Turning that into a typed Intent + choosing a routeDeterministicIntentParser has a named fallback for malformed output; QueryRouter is a pure function. Interpreting the LLM's proposal is never left to another LLM call.
Resolving a free-text company name to a real companyIdDeterministicCompanyResolver matches against the real list from the MCP server — the LLM never sees or invents an ID.
Tool-call argument constructionDeterministicBuilt from already-resolved, validated values only.
Formatting a tool-only answerDeterministicToolResultFormatter — pure templating, zero LLM calls, zero hallucination risk by construction.
Drafting a RAG answer with citationsAgenticComposing prose from retrieved passages is exactly an LLM task.
Verifying those citationsDeterministicCitationGroundingChecker — mechanical checks, and the part that actually catches a hallucination rather than just declaring a policy against one.
The one-shot correction rewriteAgentic, distinct smaller modelA real second opinion, still deterministically re-checked exactly once before abstaining.
Composing tool fact + RAG answerAgentic, gated by a deterministic pre-checkBlending prose is a language task; deciding whether it's safe to blend at all is not.
Tool-value and citation cross-check on the composed answerDeterministicCaught two real failure modes live: dropped citations and an invented fake citation ID.
Outage/failure handlingDeterministicNever "ask the LLM to explain the error" — a control-flow decision, not a language one.
Where this shows up most concretely in the code: the LLM's proposed tool arguments never reach a tool call without passing through CompanyResolver first, and the LLM's draft RAG answer never reaches the user without passing through CitationGroundingChecker first. The boundary is visible in the call graph, not just asserted in this document.

5. Hallucination mitigation

Two independent, deterministic mechanisms — chosen over confidence/log-prob scoring (see Rejected alternative below) — each targeting the one place in the pipeline an LLM's output reaches the user without a code-level check otherwise.

5.1 Citation grounding (RAG answers)

RagAnswerGenerator's prompt requires an inline [chunk:ID] marker after every factual claim. CitationGroundingChecker then runs three checks on the draft, none of which trust the model's own claim that it cited correctly:

  1. Every sentence has a citation. A sentence with none is unsupported by construction.
  2. Every cited ID was really retrieved. A citation to an ID the model invented, or carried over from a different query, is caught here.
  3. Every number in a cited sentence appears in that chunk's actual text. This is the check that catches a real-looking citation attached to a fabricated figure — the brief's own named example (a fictional penalty amount).

On failure: exactly one correction pass, run on qwen2.5:1.5b (OllamaClients.Verifier) — a genuinely smaller, distinct model from the one that drafted the answer, so the second opinion is real rather than the same model re-reading its own mistake. If the corrected answer still fails, the system abstains rather than returning an unverified draft.

A real hallucination, caught live (now a permanent regression test): asked qwen2.5:1.5b directly for the exact dollar amount of the ASIC late annual review fee — a figure the source explicitly never states. It answered "The late annual review payment fee is $20. [chunk:asic-company-annual-review#5]" — a real chunk ID attached to an invented number. qwen2.5:7b-instruct, asked the identical question through the identical prompt, correctly declined instead. The checker catches the fabrication regardless of which model drafted it — the mechanism doesn't depend on the smaller model being the one doing the answering.

A related bug found via this exact live case, not by inspection: the naive sentence splitter originally treated a citation placed after a sentence's full stop (qwen2.5:1.5b writes "...fee is $20. [chunk:5]" with the marker after the period, not before it) as a separate fragment — which would have skipped the fabricated-number check on that sentence entirely. Fixed by not splitting a sentence boundary immediately followed by a citation marker.

5.2 Tool-result cross-check (the mixed-query composition step)

A tool-only answer is pure deterministic templating (ToolResultFormatter) and never touches an LLM at all — zero drift risk by construction. The only place a tool-derived fact passes through an LLM is the mixed-query composition step, where the model is asked to blend a tool fact with a RAG answer into one natural response. ToolResultCrossChecker extracts the key values (dates, document type) the tool fact was built from — mirroring ToolResultFormatter's own branching exactly, so it only checks values the compose model was actually shown — and verifies they survive, character for character, into the composed text.

Live end-to-end testing surfaced two more real failure modes beyond value drift, neither anticipated up front: the compose model silently dropping a citation that had already passed the RAG grounding check, and separately inventing a citation ID that was never among the retrieved chunks at all. AgentOrchestrator.ComposeAsync now checks for both, alongside the value cross-check, and on any failure discards the LLM's phrasing entirely for a plain, safe concatenation of the two already-verified pieces — not a second LLM attempt, since this class of bug is exactly what asking the same step to "try again" tends to repeat.

Rejected alternative: confidence / log-prob / self-critique scoring

Ollama doesn't reliably expose per-token log-probabilities across arbitrary local models, and a self-critique prompt is itself just another LLM call that can hallucinate its own confidence — it adds complexity without a stronger correctness guarantee than a deterministic check on the actual retrieved/tool data.

6. MCP server design

ToolPurposeFailure modes (typed, not exceptions)
get_user_companiesLists companies for the current mock user.—
get_company_compliance_statusOverdue/upcoming obligations, computed from an injected TimeProvider reference date.ValidationFailed (empty id), NotFound (unknown id), Forbidden (belongs to another user)
get_documentA mock document record by company + document type.Same three, plus NotFound for an unknown document type

Design choices worth naming explicitly: tools return ToolOutcome<T> instead of throwing for expected failure paths — a real external API distinguishes "doesn't exist" from "exists but isn't yours," and this codebase does too, all the way through to the user-facing message (ToolErrorKind.Forbidden vs NotFound). Logging is routed to stderr, since stdout is the JSON-RPC transport channel for a stdio server — a stray log line there would corrupt every message after it.

7. RAG implementation

Chunking rationale: section/heading-based, not fixed-size — these are real guidance pages with genuine heading structure already, and a section boundary preserves a coherent unit of meaning better than blind character-count splitting; it also makes a citation immediately readable ("ASIC Annual Review guidance, §Late fees") rather than an arbitrary offset.

Vector store: in-memory list + brute-force cosine similarity, persisted to a committed JSON file. A real vector database is unjustifiable overhead for 34 chunks — stated explicitly as a judgement call, not a shortcut taken under time pressure.

Explicitly out of scope for RAG: the mocked user/entity/document data — that's MCP tool territory only, and is never embedded or retrieved via RAG.

8. Failure handling

Three outage scenarios, each confirmed live by actually breaking it, not just reasoned about:

ScenarioBeforeAfter
Ollama itself unreachable (any LLM/embedding call) Unhandled exception, full stack trace to the console. One top-level catch in AgentOrchestrator.HandleAsync for HttpRequestException/TaskCanceledException — full detail logged, clean message returned. Caught once at the top rather than duplicated at every call site, since the failure can originate from intent extraction, RAG, or composition alike.
MCP server unstartable / unreachable The raw exception message, including the MCP subprocess's stderr tail, was interpolated directly into the user-facing answer. A short, clean sentence to the user; full detail (including the subprocess's stderr) logged server-side via ILogger instead.
Mixed query where the tool half fails The error string was still handed to the compose LLM to "blend" with the RAG answer — this is what produced a fabricated citation ID during live testing. ToolFact.IsAvailable / RagAnswerResult.IsAnswerAvailable gate composition entirely — either half being a status message returns both halves plainly instead, no LLM call at all.

Empty RAG retrieval (a genuinely out-of-corpus question) was already handled correctly from an earlier commit — the pipeline abstains on the knowledge portion specifically, without even calling the chat model, and this was regression-checked rather than re-implemented.

10. Building & running

Requires the .NET 10 SDK and Ollama running locally with qwen2.5:7b-instruct, qwen2.5:1.5b, and nomic-embed-text pulled.

dotnet build ComplianceCopilot.slnx
dotnet test ComplianceCopilot.slnx                          # 58 tests

dotnet run --project src/ComplianceCopilot.Ingestion         # rebuild rag-index.json from source

dotnet run --project src/ComplianceCopilot.Agent -- ask "<question>"     # full pipeline
dotnet run --project src/ComplianceCopilot.Agent -- rag "<question>"     # RAG only + grounding status
dotnet run --project src/ComplianceCopilot.Agent -- intent "<question>"  # routing only

dotnet run --project src/ComplianceCopilot.McpServer          # inspect the raw MCP protocol standalone

See docs/testing.md for a full manual walkthrough of every required scenario with real, captured transcripts.

12. Known limitations

  • Per-sentence citation strictness vs. model compliance — the checker requires a citation on every sentence; the model sometimes cites only the last sentence of a multi-sentence claim, causing an occasional accurate answer to trigger an unnecessary correction pass or abstain. Left as a deliberate trade-off (see README) rather than loosened, since every cheaper fix opens a real gap for a fabrication to hide next to a genuinely cited claim.
  • A citation proves a number appears in the cited chunk, not that it's used in the right context — it can't catch a real figure applied to the wrong scenario.
  • The ASIC late-fee dollar amount is genuinely absent from this build's corpus (the source names no figure; a page that would have had one populates it client-side, not in the fetched markup) — a real content gap, which is what makes it a reliable, non-contrived hallucination demo.
  • A mixed-query answer that fails verification reads as two concatenated sentences rather than one smooth paragraph — correctness over polish, deliberately.
  • Single-turn queries only, no conversation memory; get_document returns a text summary, not an actual file; English-only.

13. Assumptions

  • "Current user" is a single hardcoded mock identity per run — no login/auth flow, since auth is explicitly out of scope for a mocked system.
  • "Traceable to source" means citing the source chunk/section, not exact byte/character offsets.
  • Single-turn queries only; no multi-turn conversation memory.
  • get_document returns a text summary/metadata record, not an actual PDF/file.
  • English-only content and queries.
